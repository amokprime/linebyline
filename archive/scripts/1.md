Notice how all the scripts are the same except for the middle section, which is documented in `Repomix snippets.md`. Would it be possible to consolidate the repetitive code in one base script with a parameter that greps a specific snippet in a code block? Then all the named scripts could just have that one line.

---
Yes — this consolidates cleanly. The shared boilerplate (paths, cleanup, zipping, clipboard) goes into one base script, and the only thing that varies is the Repomix command, which already lives as fenced code blocks in `Repomix snippets.md`. So the base script can take a section name, extract that block, and `eval` it.

One note up front: `grep` alone can't grab a multi-line block, so I use `awk` to pull the fenced block under a heading. Each named script then collapses to a single line.

## `base.sh` (the consolidated script)

````bash
#!/bin/bash
# Usage: ./base.sh <onboard|skills|build|review|test|blank>

root='/home/user/GitHub/linebyline'
upload="$root/local/upload"
unique="$(date +%s%N).zip"
md="$root/ai/chat.z.ai/Repomix snippets.md"

# lets the bare `repomix` inside the snippets resolve
export PATH="/home/user/.npm-global/bin:$PATH"

[ -z "$1" ] && { echo "Usage: $0 <snippet-name>"; exit 1; }

# Pull the fenced code block under the matching "### <name>" heading
snippet=$(awk -v target="$1" '
  /^#/ {
    h = $0; sub(/^#+[ \t]*/, "", h)
    if (tolower(h) == tolower(target)) { found = 1; next }
    if (found) exit                     # next heading = end of section
  }
  found && /^```/ {
    if (inblock) exit                   # closing fence
    inblock = 1; next                   # opening fence
  }
  found && inblock { print }
' "$md")

[ -z "$snippet" ] && { echo "No code block for '$1' in: $md"; exit 1; }

rm -f "$root/local"/*.zip
mkdir -p "$upload"
cd "$root" || exit

eval "$snippet"                         # runs repomix (or blank's empty-guard)

# nothing to zip (repomix failed, or blank with an empty upload/)
[ -z "$(ls -A "$upload")" ] && exit

cd "$upload" && zip -r "../$unique" ./*
rm -rf "$upload"/*
wl-copy "$root/local/$unique"
````

## The named scripts (one line each)

`onboard.sh`, `skills.sh`, `build.sh`, `review.sh`, `test.sh`, `blank.sh` all become:

````bash
#!/bin/bash
exec "$(dirname "$(readlink -f "$0")")/base.sh" onboard
````

…swapping the final word per script (`skills`, `build`, `review`, `test`, `blank`).

Then: `chmod +x` all of them.

## Why this works for every case

- **Repomix sections** (`onboard`, `skills`, `build`, `review`, `test`): the extracted block is just the `repomix --output … --include …` command. The base script has already `cd`'d to `$root`, so the relative `--output "local/upload/…"` and `--include` paths resolve correctly.
- **`blank`**: that section's block in the `.md` is `[ -z "$(ls -A "$upload")" ] && exit`. Since it's `eval`'d inside the base script, `$upload` expands correctly — it exits if there's nothing to zip, otherwise falls through to the zip step. The base script never clears `upload/` *before* zipping, so pre-placed supporting files survive until after the zip.

## Caveats / things to verify

1. **Heading format** — the extractor expects a markdown heading per section (`### Onboard`, `### Skills`, etc.) followed by a fenced block. If any section in the real file lacks the `###`, either add it or relax the awk match.
2. **Fence style** — I match on ```` ``` ````. The Repomix dump renders fences as single backticks, but that's likely a packing artifact. If your real file uses something else, adjust `/^```/` accordingly.
3. **First block wins** — the awk exits at the closing fence, so it captures only the Repomix command, not the example *prompt* blocks that follow some sections. That's intentional.
4. **`eval` trust** — the base script executes whatever's in that block. Fine since it's your own file, but treat `Repomix snippets.md` as executable config.
5. **Single source of truth** — the `.md` becomes the only place you edit snippet contents; the scripts stop drifting out of sync with the docs.

If you'd rather not depend on markdown formatting at all, the lower-ceremony alternative is storing each snippet as its own fragment (e.g. `snippets/onboard.sh`) and having `base.sh` just `source` the matching file — same one-line wrappers, no parsing. But if keeping the docs as the source of truth is the goal, the `awk` version above does it.

Good catch — yes, for **blank** it runs twice.

To be precise: it's only duplicated for `blank`. For the five repomix sections, the `.md` block is just the `repomix …` command, so the base-script guard is the *only* empty-check. But for `blank`, the `.md` block **is** that same check, and `base.sh` also has it after the `eval` — so blank hits it twice.

Why I had both: the `base.sh` line was meant as a universal "nothing to zip → exit" safety net (it also catches a failed `repomix`, where `upload/` ends up empty). The Blank line in the `.md` is blank's actual logic. For blank, they're the same job.

## Fix: keep it in one place

**Recommended — let `base.sh` own the guard, and make Blank's block a no-op:**

The empty-check is really shared infrastructure (zipping needs *something*), so it belongs in the base script. Then the Blank section just signals "no repomix step." Change its code block in `Repomix snippets.md` to a self-documenting no-op:

````markdown
### Blank
```sh
# no repomix — just zip the supporting files already in upload/
```
````

`eval` of a comment does nothing, so blank falls straight through to the base script's guard, which exits if `upload/` is empty or zips otherwise. No duplication, all six named scripts stay identical one-liners, and the guard still protects the repomix paths if one ever fails.

**Alternative — let the `.md` own it instead:**

If you'd rather keep the literal line documented under Blank, just delete the guard from `base.sh` (remove the `[ -z "$(ls -A "$upload")" ] && exit` after the `eval`). Then the five repomix snippets behave exactly like the originals (no extra check) and blank's check comes solely from the `.md`. The only thing you lose is the safety net for a failed `repomix` — which the originals never had anyway.

I'd go with the first: it keeps `base.sh` purely shared code and the `.md` purely per-workflow config.

Is this kind of practice (using a non-code markdown file as a library for Bash script code files) likely to be flagged as a code smell or vulnerability? For instance, do I need to exclude this scripts directory from SonarCloud GitHub Actions scans?

---
Short version: **it's not a real vulnerability in your trust model, but it is the kind of thing linters flag — and the `.md` is the least of your worry; it's the `eval` in `base.sh` that would get attention.** You probably don't *need* to exclude the directory, but you may *want* to. Here's the breakdown.

## Vulnerability: basically no, with one caveat

The only executed content is what `awk` pulls out of the `.md`. Critically, the CLI parameter is used safely — it's only compared as data (`tolower(h) == tolower(target)`), never interpolated into executed code. So there's no injection via the argument.

The real question is: *do you trust the file being `eval`'d?* It's committed by you to your own repo, with no runtime user input feeding it. In that model there's no exploitable attack surface. The caveat: `eval`-of-file-content is a classic injection vector **in the general case**, so if this repo ever becomes public and accepts PRs, a malicious edit to `Repomix snippets.md` would run as your user the next time you invoke a script. Private single-user repo → negligible. Public + contributions → treat that `.md` as executable.

## Code smell: mildly yes, but the practical cost is maintainability, not security

It's not a named anti-pattern, but it combines two things reviewers flag: executing code sourced from a doc file, and `eval`. For personal tooling that's a fine pragmatic trade. The downsides you'll actually feel:

- **The embedded bash is invisible to your tooling.** SonarShell, `shellcheck`, etc. don't parse fenced code blocks, so the real commands get no linting.
- **It's brittle to formatting.** Renaming a heading or changing fence style silently breaks the `awk` extraction.
- **Reduced greppability** — you can't trace "where is build run" the usual way.

## SonarCloud specifics

- **The `.md`:** SonarCloud generally does not extract and analyze fenced code blocks as shell, so `Repomix snippets.md` won't generate shell findings.
- **The `.sh` files:** these *will* go through the shell analyzer. The one-liners and boilerplate are benign; `eval "$snippet"` in `base.sh` is the likely hit if your active ruleset covers dynamic execution (many SAST toolsets flag it as a security hotspot). The hardcoded `/home/user` paths won't be treated as secrets.
- Whether it actually trips your **quality gate** depends on the rule's severity and your gate config.

## Do you need to exclude?

Not for security — exclusion is a scoping/noise decision, not a fix. Two reasonable paths:

1. **Keep in scope, triage.** Let it scan, then mark the `eval` finding as *won't fix / false positive* with a note that the source is a trusted committed file. Most honest option.
2. **Exclude as tooling.** Since these are templates copied into a non-tracked `local/` (per the README) rather than product code, scoping them out is common and defensible:
   ```properties
   sonar.exclusions=ai/chat.z.ai/scripts/**
   ```

I'd lean toward (1) so you don't blunt-instrument a directory that could later hold real code, and only exclude if the finding becomes persistent noise.

One optional hardening note: if you ever want to drop the smell entirely, store each snippet as a real `snippets/<name>.sh` fragment and `source` it — no `eval`, no markdown parsing, and the fragments become lintable again. That abandons the "docs as the library" goal though, so it's a preference call, not a requirement.

## `base.sh`

````bash
#!/bin/bash
# Usage: ./base.sh <onboard|skills|build|review|test|blank>

root='/home/user/GitHub/linebyline'
upload="$root/local/upload"
unique="$(date +%s%N).zip"
snippets="$root/ai/chat.z.ai/scripts/snippets"

# single place to point at repomix
export PATH="/home/user/.npm-global/bin:$PATH"

[ -z "$1" ] && { echo "Usage: $0 <snippet-name>"; exit 1; }
fragment="$snippets/$1.sh"
[ -r "$fragment" ] || { echo "No such snippet: $fragment"; exit 1; }

rm -f "$root/local"/*.zip
mkdir -p "$upload"
cd "$root" || exit

. "$fragment"     # sourced (not subshelled) so blank's `exit` stops the script

cd "$upload" && zip -r "../$unique" ./*
rm -rf "$upload"/*
wl-copy "$root/local/$unique"
````

The key is `. "$fragment"` (source) rather than running it in a subshell — that's what lets `blank.sh`'s `exit` actually stop the whole script, and it's why the fragment can use `$upload` without it being exported.

## The markdown becomes pointers

Replace each fenced command with a one-line pointer, keeping the surrounding prose:

````markdown
### Onboard
Command: `scripts/snippets/onboard.sh`
- Workflows always start with the Onboard step, including dedicated sessions:
`
Follow `*-SKILL.md` files as rules. This is the Onboard step.
`

A plain `code` path is greppable and unambiguous; if you want it clickable in Obsidian, `[[ai/chat.z.ai/scripts/snippets/onboard|onboard snippet]]` works too (it just won't preview the shell file inline).

## What you gain

- **One place to customize.** Fragments use relative paths plus inherited `$root`/`$upload`, so only `base.sh` carries `/home/user` and the repomix location. The old "replace the path in all six scripts" step collapses to editing one file.
- **Lintable snippets.** `shellcheck` now sees the real commands.
- **No duplicated commands** — the `.md` documents intent, the fragment is the implementation.

One thing to stay aware of: because fragments are sourced into `base.sh`'s shell, a fragment *can* affect the parent (the `exit` in `blank.sh` is the intended case, but a stray `cd` or variable assignment would leak too). For trusted local fragments that's fine — just don't treat the `snippets/` files as isolated, side-effect-free configs.

Wouldn't it be simpler to fold the fragments into the wrappers, so there's only one `onboard.sh` and so on?

---
Yes — and honestly that's the cleaner outcome. The `snippets/` split only existed to keep the wrappers as *pure one-liners*. If you relax that slightly, folding removes the same-name indirection (`onboard.sh` wrapper + `snippets/onboard.sh` fragment) and leaves you with exactly one file per workflow.

The way to do it without re-duplicating the boilerplate: `base.sh` becomes a **sourced library** that runs the shared flow and calls a hook, and each wrapper just defines its command.

## `base.sh` (sourced, not executed)

````bash
# base.sh — sourced by each workflow script, which must define snippet() first
root='/home/user/GitHub/linebyline'
upload="$root/local/upload"
unique="$(date +%s%N).zip"

export PATH="/home/user/.npm-global/bin:$PATH"

type snippet >/dev/null 2>&1 || { echo "snippet() not defined by caller"; exit 1; }

rm -f "$root/local"/*.zip
mkdir -p "$upload"
cd "$root" || exit

snippet                                  # the workflow-specific command

cd "$upload" && zip -r "../$unique" ./*
rm -rf "$upload"/*
wl-copy "$root/local/$unique"
````

## Each workflow script = its command + one source line

````bash
#!/bin/bash
# onboard.sh
snippet() {
  repomix --output "local/upload/repomix-onboard.xml" \
    --include-full-directory-structure \
    --include "package.json,README.md,\
ai/chat.z.ai/skills/project-workflow-SKILL.md,\
ai/chat.z.ai/skills/web-channel-SKILL.md,\
ai/chat.z.ai/skills/skill-SKILL.md,\
archive/modular/plan/**"
}
. "$(dirname "$(readlink -f "$0")")/base.sh"
````

````bash
#!/bin/bash
# blank.sh
snippet() {
  [ -z "$(ls -A "$upload")" ] && exit
}
. "$(dirname "$(readlink -f "$0")")/base.sh"
````

Because `base.sh` is sourced into the same shell, blank's `exit` still stops the whole script, and `$upload` is visible inside `snippet()` at call time. The markdown now just points at the wrapper itself (`Command: scripts/onboard.sh`) — still one copy of each command, no fragments directory.

Result:
```
ai/chat.z.ai/scripts/
  base.sh
  onboard.sh  skills.sh  build.sh  review.sh  test.sh  blank.sh
```

## Trade-off to be aware of

You're swapping "one-line wrapper + separate fragment" for "one self-contained file that's ~2 lines of glue + the command." The wrappers are no longer literal one-liners, but the boilerplate is still fully centralized in `base.sh`, the command is still lintable, and the naming collision is gone. For your stated goal (one `onboard.sh`, no duplication), this is the better fit.

One small gotcha carried over from before: keep the continuation lines **inside** the multi-line `--include "…"` at column 0 (as shown), or the indentation leaks into the comma list.

If you'd rather not have the implicit `snippet` hook, the alternative is `base.sh` exposing `setup` and `finalize` functions and each wrapper calling `setup` → its command → `finalize`. More explicit, but then each wrapper can forget a step — the hook version guarantees the orchestration.
