## Turn 1

### User:

How to git diff all changes (currently unstaged) since last commit into a machine-readable file for AI review?

---
### Agent:

Use a plain unified diff with color/pager/external-diff disabled. That is already machine-readable and easy for an AI to review.

#### 1. Only unstaged tracked changes

```bash
git --no-pager diff \
  --no-color \
  --no-ext-diff \
  --unified=5 \
  > ai-review.diff
```

This is `working tree` vs `index`. If you have staged changes too, they will **not** be included.

#### 2. All tracked changes since the last commit

If by “since last commit” you mean `HEAD`, including staged + unstaged tracked changes:

```bash
git --no-pager diff HEAD \
  --no-color \
  --no-ext-diff \
  --unified=5 \
  > ai-review.diff
```

If you have nothing staged, this is the same as `git diff` for tracked files.

#### 3. Include untracked files too

`git diff` does **not** include untracked files. To include them without changing your index:

```bash
{
  git --no-pager diff HEAD --no-color --no-ext-diff --unified=5

  git ls-files --others --exclude-standard -z |
    while IFS= read -r -d '' f; do
      git --no-pager diff --no-index \
        --no-color \
        --no-ext-diff \
        --unified=5 \
        -- /dev/null "$f" || true
    done
} > ai-review.diff
```

If you want only unstaged tracked changes plus untracked files, replace the first `git diff HEAD` with `git diff`.

#### Simpler shortcut, if nothing is staged

```bash
git add -N .
git --no-pager diff HEAD --no-color --no-ext-diff --unified=5 > ai-review.diff
git reset
```

`git add -N` marks untracked files as intent-to-add so they appear in `git diff HEAD`.  
Warning: `git reset` will unstage anything that was already staged, so use this only when your index is clean.

#### Useful flags

- `--no-color` — no ANSI escapes
- `--no-ext-diff` — don’t invoke external diff tools
- `--unified=5` — more context for AI review
- `--binary` — only if you need a patch that can be applied; not useful for AI reading binary files
- `-- . ':(exclude)package-lock.json'` — exclude noisy/generated files

Then feed `ai-review.diff` to your AI review prompt.

## Turn 2

### User:

So to show ALL local changes the agent would not see from cloning my last public commit, I should stage everything first?

---
### Agent:

No. Staging everything is not the right mental model, and it’s not necessary.

The agent cloning your last public commit will see exactly that commit. Anything after it — local commits **and** uncommitted changes — is invisible to them. So you want:

> diff the current working tree against the last public commit

not:

> stage everything and diff against `HEAD`

Staging only changes the index. It does not help with local commits, and it only “helps” with untracked files as a side effect.

#### Correct approach

Set the last public commit:

```bash
PUBLIC=origin/main   # or the SHA/tag you last pushed
```

Then capture all tracked changes since that commit:

```bash
git --no-pager diff "$PUBLIC" \
  --no-color \
  --no-ext-diff \
  --unified=5 \
  > ai-review.diff
```

This includes:
- local commits after `$PUBLIC`
- staged changes
- unstaged changes

It does **not** include untracked files.

#### Include untracked files too

Safest way, without touching your index:

```bash
{
  git --no-pager diff "$PUBLIC" --no-color --no-ext-diff --unified=5

  git ls-files --others --exclude-standard -z |
    while IFS= read -r -d '' f; do
      git --no-pager diff --no-index \
        --no-color \
        --no-ext-diff \
        --unified=5 \
        -- /dev/null "$f" || true
    done
} > ai-review.diff
```

That gives you one machine-readable diff of everything the agent would not see from cloning `$PUBLIC`.

#### If you really want to stage everything first

You can do this:

```bash
PUBLIC=origin/main
git add -A
git --no-pager diff "$PUBLIC" --no-color --no-ext-diff --unified=5 > ai-review.diff
git reset
```

But note:
- `git add -A` stages untracked files so they appear in the diff.
- `git reset` unstages everything, which can be bad if you had intentionally staged things.
- It still does **not** fix the main issue if you diff against `HEAD` instead of `$PUBLIC`.

So: don’t stage everything first. Diff against the last public commit, and add untracked files explicitly if you need them.

### Agent:

Right — the base is a SHA, not a branch. Branch names move; use the commit hash so the agent gets exactly what you saw. Then give them a patch they can apply, plus enough metadata to reconstruct the state.

#### The base ref

Find the last public commit on `staging`:

```bash
git log --oneline staging
#### or the exact SHA you last pushed:
BASE=<sha>
```

Use the SHA. If `staging` has since moved, a branch name would be wrong.

#### One-shot reproducible bundle

Two files: a binary-safe patch, and metadata telling the agent how to apply it.

```bash
BASE=<sha>   # last public commit

#### 1. Mark untracked files as intent-to-add so they appear in the diff
git add -N .

#### 2. Full patch from BASE to your current working tree (staged + unstaged + untracked)
git --no-pager diff --binary "$BASE" > changes.patch

#### 3. Undo the intent-to-add so your index is unchanged
git reset -q

#### 4. Metadata so the agent can reconstruct state
{
  echo "base_sha: $BASE"
  echo "head_sha: $(git rev-parse HEAD)"
  echo "branch:   $(git rev-parse --abbrev-ref HEAD)"
  echo "status:"
  git status --porcelain
} > changes.meta
```

Give the agent `changes.patch` and `changes.meta`.

#### What the agent does

```bash
git clone <your-public-repo> work && cd work
git fetch origin "$BASE"          # must exist publicly
git checkout "$BASE"

git apply --binary changes.patch  # reproduces tracked + untracked changes
```

They land in exactly your working tree state, on the base commit. If they want your branch name too, they can `git checkout -b staging`.

#### Notes

- `--binary` matters if any changed file is binary; without it, `git apply` will fail on binary hunks.
- `git add -N .` only touches untracked files; `git reset -q` undoes it. If you already had staged changes, do this on a clean index, or accept that the reset unstages them too.
- If the agent can't fetch `$BASE` (private, force-pushed away), replace `changes.patch` with a `git bundle` of the commits and a separate patch for the working tree:

```bash
git bundle create commits.bundle "$BASE"..HEAD
git --no-pager diff --binary HEAD > working.patch
```

  Bundle covers your commits; `working.patch` covers staged/unstaged/untracked. That's fully offline-reproducible and doesn't depend on `$BASE` being reachable in the remote.

#### Why origin/staging

- It is the shared ref everyone can see after `git fetch` / clone. The agent will have it.
- Local `staging` is per-machine. Yours may be ahead of the remote (unpushed commits), behind it, or diverged. `origin/staging` is not.
- Your log shows them pointing at the same commit today, but that's not guaranteed tomorrow, and the whole point is "the last *public* commit."

`staging` is only correct if you personally guarantee it always equals `origin/staging`. That's a habit, not a property.

#### Fetch first, so the ref is current

```bash
git fetch origin staging
BASE=origin/staging
```

Without the fetch, `origin/staging` is whatever your last `git fetch`/`pull` left it at. Stale remote-tracking refs are a common footgun.

#### Freeze the SHA in metadata

You want "no SHA" in the script, but reproducibility needs a fixed point. Do both — resolve at runtime:

```bash
BASE=origin/staging
BASE_SHA=$(git rev-parse "$BASE")

git add -N .
git --no-pager diff --binary "$BASE_SHA" > changes.patch
git reset -q

{
  echo "base_ref: $BASE"
  echo "base_sha: $BASE_SHA"
  echo "head_sha: $(git rev-parse HEAD)"
  echo "branch:   $(git rev-parse --abbrev-ref HEAD)"
  echo "status:"
  git status --porcelain
} > changes.meta
```

The script refers to `origin/staging` (flexible, self-updating). The patch is taken against the resolved SHA (stable, reproducible even if `origin/staging` moves before the agent applies it).

#### For the agent

```bash
git clone <repo> work && cd work
git checkout "$(grep '^base_sha:' changes.meta | awk '{print $2}')"
git apply --binary changes.patch
```

They still need the base commit to exist publicly — which it does, since it was `origin/staging` at the time you built the patch.

So: **`origin/staging` in the script, SHA frozen in the metadata.** Not local `staging`.

`git fetch origin staging` is correct. `git fetch origin/staging` is not — git would look for a *remote* literally named `origin/staging` and fail with `fatal: 'origin/staging' does not appear to be a git repository`.

But there are two real bugs and one footgun in the script as written.

#### Bugs

**1. `BASE_SHA` is resolved before `cd` and before `fetch`.**

```bash
BASE=origin/staging
BASE_SHA=$(git rev-parse "$BASE")   # ← wrong repo, and stale

cd ~/GitHub/linebyline
git fetch origin staging
```

If you invoke the script from anywhere else, `rev-parse` runs in the wrong repo. Even from the right repo, it resolves `origin/staging` *before* the fetch, so you get the pre-fetch SHA — exactly the staleness the fetch was supposed to fix. Order must be: `cd` → `fetch` → `rev-parse`.

**2. `git reset -q` clobbers anything you had staged.**

`git add -N .` only adds intent-to-add for untracked files, but `git reset -q` with no paths unstages *everything* — including files you deliberately staged before running the script. If your index wasn't clean, you lose that.

#### Corrected

```bash
#!/bin/bash
set -euo pipefail

cd ~/GitHub/linebyline

BASE_REF=origin/staging
git fetch origin staging
BASE_SHA=$(git rev-parse "$BASE_REF")

#### snapshot untracked files so we can undo only their intent-to-add
NEWFILES=$(mktemp)
git ls-files --others --exclude-standard -z > "$NEWFILES"

#### status BEFORE we touch the index — this is the state the agent should match
git status --porcelain > scratch/upload/changes.status

git add -N .
git --no-pager diff --binary "$BASE_SHA" > scratch/upload/changes.patch

#### undo only the intent-to-add; leave anything you had already staged alone
xargs -0 -r git reset -q -- < "$NEWFILES"
rm -f "$NEWFILES"

{
  echo "base_ref: $BASE_REF"
  echo "base_sha: $BASE_SHA"
  echo "head_sha: $(git rev-parse HEAD)"
  echo "branch:   $(git rev-parse --abbrev-ref HEAD)"
  echo "status:"
  cat scratch/upload/changes.status
} > scratch/upload/changes.meta
```

Key changes:

- `set -euo pipefail` — a bad fetch or missing remote should abort, not silently produce a patch against a stale base.
- `cd` first, then `fetch`, then `rev-parse`.
- Capture untracked file list, `add -N`, then `git reset -- <those files>` instead of a blanket reset. Your pre-existing staged changes survive.
- `git status --porcelain` is captured before mutating the index. Same output either way if the reset works, but this makes it obvious and survives a partial failure.

#### Minor

- `scratch/upload/` must exist; otherwise the redirects fail. `mkdir -p scratch/upload` at the top if it's not guaranteed.
- `git -C ~/GitHub/linebyline` would let you drop the `cd` entirely and avoid subshell-relative-path confusion, but `cd` is fine.
- The final `changes.meta` still records `base_sha`, which is what makes `changes.patch` reproducible even if `origin/staging` moves between now and when the agent applies it. Keep that.

### User:

Where to put the git -C if doing it that way?

---
### Agent:

`git -C <path>` goes immediately after `git`, before the subcommand, on every git invocation:

```bash
git -C ~/GitHub/linebyline fetch origin staging
git -C ~/GitHub/linebyline rev-parse origin/staging
```

There is no "set it once" form — `-C` is a per-invocation flag, not a persistent option. So you either repeat it, or you set a variable and use it.

#### Option A — repeat it

```bash
#!/bin/bash
set -euo pipefail

REPO=~/GitHub/linebyline
OUT=~/GitHub/linebyline/scratch/upload

git -C "$REPO" fetch origin staging
BASE_SHA=$(git -C "$REPO" rev-parse origin/staging)

git -C "$REPO" ls-files --others --exclude-standard -z > "$OUT/newfiles.z"
git -C "$REPO" status --porcelain > "$OUT/changes.status"

git -C "$REPO" add -N .
git -C "$REPO" --no-pager diff --binary "$BASE_SHA" > "$OUT/changes.patch"
xargs -0 -r git -C "$REPO" reset -q -- < "$OUT/newfiles.z"
rm -f "$OUT/newfiles.z"
```

Note `--no-pager` also goes after `git` but after `-C` — flag order among `git`'s own global options is `git -C <path> --no-pager diff ...`. Both are global; `-C` just conventionally comes first.

#### Option B — variable wrapper

Cleaner, and what I'd actually use:

```bash
#!/bin/bash
set -euo pipefail

REPO=~/GitHub/linebyline
OUT="$REPO/scratch/upload"

g() { git -C "$REPO" "$@"; }

g fetch origin staging
BASE_SHA=$(g rev-parse origin/staging)

g ls-files --others --exclude-standard -z > "$OUT/newfiles.z"
g status --porcelain > "$OUT/changes.status"

g add -N .
g --no-pager diff --binary "$BASE_SHA" > "$OUT/changes.patch"
xargs -0 -r g reset -q -- < "$OUT/newfiles.z"
rm -f "$OUT/newfiles.z"

{
  echo "base_ref: origin/staging"
  echo "base_sha: $BASE_SHA"
  echo "head_sha: $(g rev-parse HEAD)"
  echo "branch:   $(g rev-parse --abbrev-ref HEAD)"
  echo "status:"
  cat "$OUT/changes.status"
} > "$OUT/changes.meta"
```

`g` is the whole point: every call is scoped to `$REPO`, paths in `$OUT` are absolute so redirects don't depend on cwd, and there's no `cd` mutating your shell.

#### Which to prefer

`-C` beats `cd` here because:
- Redirect targets and `mktemp` stay relative to wherever you ran the script, not the repo.
- No `cd` means no accidental interaction with `CDPATH`, no subshell needed, no surprise if the script is sourced instead of executed.
- It's explicit per command, so a reader never has to remember "we're in the repo now."

Either form is fine; just don't mix — pick `-C` everywhere or `cd` once at the top. Mixing is how you get a `rev-parse` quietly resolving against the wrong tree.

#### 2. Does the index get permanently touched? (the "Heisenberg" question)

Yes, the script **writes to `.git/index`** — `git add -N` is not read-only. But `git reset -- <files>` restores it, so after a successful run there's no persistent change: no commits, no moved refs, no reflog entries, no staged content. The only artifacts are the files in `scratch/upload/`.

Two things worth being precise about:

- `git add -N .` is *not* `git add .`. It records an empty index entry (intent-to-add), no blob. Even if it leaked, your files aren't staged.
- `git add -N .` doesn't touch entries that are already staged, and `git reset -- <newfiles>` only clears the ones you just added. So pre-existing staged changes survive. That's why the targeted reset matters versus a blanket `git reset -q`.

The real residue case is a **crash between `add -N` and `reset`** — then the intent-to-add entries remain until you `git reset` them. Guard it with a trap:

```bash
NEWFILES=$(mktemp)
POST=$(mktemp)

reset_ita() {
  [ -s "$NEWFILES" ] && xargs -0 -r g reset -q -- < "$NEWFILES" || true
  : > "$NEWFILES"
}
trap 'reset_ita; rm -f "$NEWFILES" "$POST"' EXIT INT TERM
```

`reset_ita` is idempotent; the second call after the explicit reset finds `NEWFILES` empty and does nothing.
