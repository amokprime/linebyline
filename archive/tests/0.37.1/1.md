Yes — those two commands from the repo root in Zed's terminal will get you 90% of the way. A few things to know before you run them on Fedora 44 KDE.

## What's fine

- **Fish shell**: no issue. Both `npm install` and `npx playwright install` are shell-agnostic. Zed's integrated terminal is just a pty.
- **Node**: Fedora 44 ships Node 22+, well above Playwright 1.59's minimum. If `node -v` returns 18+ you're set.
- **`npx serve . -l 3004`** (the `webServer` in `playwright.config.js`): `serve` isn't in `package.json`, but npx will fetch it on first use. Works the same on Linux.
- **Test helpers**: `tests/helpers/index.js` uses `path.resolve()` and `fs` — fully cross-platform. The `archive/semantic/X.X.X/linebyline-X.X.X.html` lookup will work as-is.

## Gotchas to expect

**1. System deps — run this right after `npx playwright install`:**
```fish
npx playwright install-deps
```
Fedora doesn't ship everything Chromium/Firefox/WebKit need (libnss3, alsa-lib, gtk3, mesa-dri-drivers, etc.). `install-deps` will `sudo dnf install` the full list for you. Without this, `npx playwright test` fails on first launch with cryptic "error while loading shared libraries" messages.

**2. Snapshot filenames are platform-suffixed — this is the big one.**
Every snapshot file in `tests/` is named like `landing-1-firefox-win32.png`, `split-paren-lines-firefox-win32.txt`, etc. Playwright auto-appends `-{browser}-{platform}` to snapshot lookups. On Linux it'll look for `*-firefox-linux.{png,txt}` — which don't exist — so **every** `toMatchSnapshot()` / `toMatchAriaSnapshot()` test will fail on the first run.

Two paths forward:
- **Adopt Linux as the new baseline**: `npx playwright test --update-snapshots` once, then commit the new `-linux` files. Cleanest if you're switching permanently.
- **Keep Windows snapshots alongside**: just run the update; Playwright stores both suffixes side-by-side, so Windows contributors still get their `-win32` files matched. No conflict.

Either way, plan for one regeneration pass.

**3. Line endings in committed `.txt` snapshots.**
If the repo was committed from Windows with CRLF preserved, Linux Git checkout gives LF, and the committed snapshot text files might still contain `\r`. Quick check after install:
```fish
rg -l '\r$' tests/
```
If you see hits in `*-snapshots/`, those text snapshots were stored CRLF. Regenerating with `--update-snapshots` on Linux will normalize them to LF — fine, but flag it in the commit so Windows reviewers know to set `core.autocrlf=input` or similar.

**4. WebKit (Safari) project may be flakier on Fedora.**
`playwright.config.js` runs three projects: chromium, firefox, webkit. WebKit on Fedora sometimes needs `webkit2gtk3` and friends that `install-deps` mostly handles but not always perfectly. If you only care about the Firefox baseline (which is what your existing snapshots are tagged with), scope runs to it:
```fish
npx playwright test --project=firefox
```

**5. AHK scripts in `archive/autohotkey` are Windows-only.**
Mentioned in your README — irrelevant for tests, but if you actually used those hotkey workarounds in your real workflow, look at AutoKey or keyd on Linux. Not a blocker for getting the test suite green.

**6. Wayland vs X11 on KDE Plasma 6.**
Playwright runs headless by default in CI; locally `npx playwright test` is also headless unless you pass `--headed`. Headless is unaffected by your session type. If you do go `--headed` and hit input weirdness, that's Wayland grabbing certain key combos (Alt+Tab, Super) — your test shortcuts are all `Control+...` so you should be fine, but worth knowing.

## Recommended first-run sequence


## Fish conversions

Fish has no `.bashrc` — aliases live as functions under `~/.config/fish/functions/`. The idiomatic way is to define a function and `funcsave` it. Note that fish uses `(cmd)` for command substitution (the bash `$(cmd)` also works in fish 3.4+, but `(cmd)` is what everyone uses).

Open a fish shell and paste these one by one:

```fish
# cgn — codegen against the latest versioned HTML.
# No fixed browser; default is chromium. Pass --browser firefox / webkit to override.
function cgn
    set -l path (node -e "const{findLatestVersion}=require('@linebyline/test-helpers');process.stdout.write(findLatestVersion())")
    npx playwright codegen "http://localhost:3004$path" $argv
end
funcsave cgn

# tsta — UI mode, all projects.
function tsta
    npx playwright test --ui $argv
end
funcsave tsta

# tst — headless run, all three projects (chromium, firefox, webkit).
function tst
    npx playwright test $argv
end
funcsave tst
```

A few notes:

- `$argv` is appended so you can still scope ad-hoc — e.g. `tst --project=firefox` or `tst tests/mark.spec.js` works without redefining anything.
- `funcsave` writes the function to `~/.config/fish/functions/cgn.fish` etc., so it survives shell restarts. New terminals pick it up automatically; the current shell already has it.
- For codegen, Playwright only supports one `--browser` per invocation, so "all three" means running `cgn --browser chromium`, `cgn --browser firefox`, `cgn --browser webkit` separately. The default (no flag) is chromium. If you want a one-shot loop:
  ```fish
  for b in chromium firefox webkit
      cgn --browser $b
  end
  ```
  But codegen opens an interactive inspector window, so you'll be doing them sequentially anyway.

## Fedora snapshots vs GitHub Ubuntu runners

Short answer: **text and aria snapshots yes, PNG screenshots probably not.**

Looking at the snapshot files in your repo, they fall into three categories:

| Type | Extension | Platform suffix? | Portable Fedora → Ubuntu? |
|---|---|---|---|
| Aria snapshots | `.aria.yml` | No (e.g. `merge-two-1.aria.yml`) | ✅ Yes — pure text |
| Text snapshots | `.txt` | Yes (`-firefox-linux.txt`) | ✅ Yes — content is plain text |
| Image snapshots | `.png` | Yes (`-firefox-linux.png`) | ⚠️ Probably not |

Playwright tags snapshots with `-{browser}-{platform}` using `process.platform`. Both Fedora and Ubuntu resolve to `linux`, so the **filenames** collide and CI will look up your Fedora-generated files. The question is whether the **pixels** match.

For `.txt` and `.aria.yml` — no rendering involved, just DOM text/structure. Fully portable. Commit them once on Fedora, CI will match forever.

For `.png` — this is where it gets nasty. Chromium and Firefox on Linux render text through Pango + fontconfig + freetype, and the output depends on:

- **Installed system fonts.** Fedora 44 and Ubuntu 22.04/24.04 ship different default sans/serif stacks. Your `index.html` likely uses something like `system-ui` / `sans-serif`, which resolves to Cantarell on Fedora and Ubuntu on Ubuntu. Different glyph widths → different text wrapping → different button sizes → pixel diff fails.
- **Font hinting and subpixel rendering settings.** KDE Plasma 6 on Wayland applies its own hinting/antialiasing defaults via `~/.config/fontconfig/`. Headless CI has none of that — but the underlying library versions still differ.
- **Pango / harfbuzz versions.** Fedora 44 is bleeding edge; GitHub's Ubuntu LTS is conservative. Different versions can produce subtly different glyph positioning even for the same font.
- **Mesa / Skia builds** for Chromium. Different distro patches, different rasterisation edge cases.

Playwright's official guidance is that image snapshots are **not** guaranteed stable across OSes. You'll see this the first time CI runs: a few PNGs will fail with diffs in the 0.1%–2% pixel range, almost entirely around text.

### What to do

Pick one of these, in rough order of robustness:

1. **Drop PNG snapshots entirely for cross-platform use.** Your `.aria.yml` snapshots already cover most of what the PNGs assert (button visibility, layout structure, labels). If a PNG is only checking "does this button exist and have the right label", the aria snapshot already does that better. Audit `tests/*.spec.js` for `toMatchSnapshot('...png')` calls and consider replacing with `toMatchAriaSnapshot()` or `toBeVisible()` + `toHaveText()`.

2. **Pin a web font.** Add a `@font-face` rule in `index.html` that loads a specific font file (e.g. commit a `.woff2` of Inter or whatever you use), and set `font-family: 'Inter', sans-serif` on `:root`. Now every system renders the same glyphs. This eliminates ~80% of cross-distro PNG drift. Combined with `screenshot.animations: 'disabled'` in `playwright.config.js`, you can get reliable cross-OS PNGs.

3. **Set a tolerance threshold.** In `playwright.config.js`:
   ```js
   expect: {
     toHaveScreenshot: { maxDiffPixelRatio: 0.01 },
   },
   ```
   Lets small font-rendering differences pass. Works, but you'll occasionally get a real regression hidden in the noise.

4. **Regenerate PNGs on CI, don't commit them.** Add `*.png` to `.gitignore` and let CI generate-then-test in a single workflow. Cleanest, but CI runs slower and you lose local PNG diffs.

5. **Per-OS snapshots via custom project names.** Rename your config projects so Fedora gets `-linux-fedora` and CI gets `-linux-ubuntu`. Doable by overriding `snapshotPathTemplate` per project, but you'd be maintaining two sets of PNGs forever. Not recommended.

My recommendation: do (1) aggressively for any PNG that's really just checking structure, and (2) for the handful of PNGs that genuinely need pixel-level visual regression (theme colors, button tint). Skip (3)/(4)/(5) unless you hit a wall.

For the first run on Fedora, expect:
- All `.aria.yml` and `.txt` snapshots: regenerate cleanly with `--update-snapshots`, commit, done.
- All `.png` snapshots: regenerate locally, commit, push, watch CI — fix the handful that fail with the strategy above.

Welcome to the unsupported-but-works-fine club. Here's what happened and how to fix it.

## What's going on

Playwright doesn't officially support Fedora. When it detects an unsupported distro, it falls back to downloading the **Ubuntu 24.04 build** of each browser (which works fine on Fedora because Fedora 44's glibc is newer than Ubuntu's — backward-compatible). The `install-deps` script, however, doesn't have a Fedora code path — it just tries `apt-get`, which doesn't exist on Fedora.

Good news: the Ubuntu 24.04 binaries that Playwright downloads **are the same binaries GitHub's Ubuntu runners use**. So your earlier concern about Fedora-vs-CI rendering differences is smaller than feared — same Chrome for Testing 147, same Firefox 148, same WebKit 26.4. The only remaining drift sources are system font stacks and fontconfig/pango versions.

## Install the deps yourself

One-shot dnf command:

```fish
sudo dnf install -y \
  libicu harfbuzz-icu libjpeg-turbo libmanette hyphen libwoff \
  nss nspr atk at-spi2-atk cups-libs \
  libXcomposite libXdamage libXrandr libXtst libXScrnSaver \
  mesa-libgbm mesa-libgl pango cairo cairo-gobject gtk3 \
  dbus-glib libdrm libxkbcommon alsa-lib \
  libwpe wpebackend-fdo enchant2 \
  gstreamer1-plugins-base gstreamer1-plugins-bad-free-extras gstreamer1-plugins-good
```

Notes:

- **`libwoff`** is the only one I'm not 100% sure exists under that name in Fedora 44. If dnf errors on it, drop it from the list — `webkit2gtk3` and the WPE packages usually cover WOFF support on Fedora. If any test fails later complaining about `libWPEWebKit` or WOFF, run `dnf provides 'libwoff*'` to find the actual package name.
- **`gstreamer1-plugins-bad-free-extras`** is in Fedora's main repo, no RPM Fusion needed. If you want MP4/H.264 playback in WebKit tests, you'll additionally need `gstreamer1-plugins-ugly-free` from RPM Fusion, but for headless test runs of LineByLine (which uses MP3 audio, not video) you likely don't need that.
- **`webkit2gtk3`** is intentionally absent from my list — Playwright ships its own WebKit binary and links against the *runtime* deps above, not the full WebKitGTK dev stack.

## Verify before running tests

After the dnf install finishes, Playwright won't re-validate. You'll only find out about missing libs when a browser fails to launch. A quick way to pre-flight each engine:

```fish
npx playwright launch chromium --headless --detach  # then Ctrl-C
npx playwright launch firefox  --headless --detach
npx playwright launch webkit   --headless --detach
```

Actually the simpler check — just start the test suite against a single spec:

```fish
npx playwright test --project=chromium --list  # dry-run, validates config
npx playwright test --project=chromium tests/smoke.spec.js  # one real run
```

If chromium launches cleanly, firefox and webkit usually do too (firefox is the least picky; webkit is the most). Any missing lib will surface as `error while loading shared libraries: libFoo.so.x: cannot open shared object file` — find the Fedora package with:

```fish
dnf provides 'libFoo.so*'
```

Then `sudo dnf install` it and re-run.

## The unsupported-Fedora situation, long-term

Two things to be aware of:

1. **It works today and has for years.** Playwright's Ubuntu fallback is stable, the binaries are glibc-compatible with newer distros, and Fedora 44 KDE has nothing exotic that breaks them.
2. **If Playwright ever drops the fallback**, you'd need to switch to running tests via Docker (`mcr.microsoft.com/playwright:v1.59.1-jammy`) — same Ubuntu environment as CI. Annoying but not catastrophic. For now, no action needed.

Order matters — `--update-snapshots` is a flag that takes an optional mode argument (`all`, `changed`, `missing`, `none`), so the spec file path can't come right after it. Put the flag before the path, or use `=` to bind the mode explicitly.

## Two ways to fix it

```fish
# Option A: flag before path, default mode (all)
npx playwright test --update-snapshots --project=chromium tests/smoke.spec.js

# Option B: explicit mode (same result for first run)
npx playwright test --update-snapshots=all --project=chromium tests/smoke.spec.js
```

Both work. Option A is what you'll type 99% of the time.

## The four modes, for reference

| Mode | What it does |
|---|---|
| `all` | Overwrite every snapshot, even ones that currently pass. Use for a clean re-baseline. |
| `changed` | Only update snapshots that are currently failing. Preserves passing ones. |
| `missing` | Only create snapshots that don't exist yet. **This is what you actually want for the first run** — it won't touch your existing `-win32.png` files or any `-linux.png` you've already created, only fills in the gaps. |
| `none` | Don't update anything. Same as omitting the flag. |

For your first Linux run, `missing` is safer than `all` — it guarantees you won't accidentally overwrite a passing snapshot with a subtly-wrong one if a test happens to be flaky during the run:

```fish
npx playwright test --update-snapshots=missing --project=chromium tests/smoke.spec.js
npx playwright test --update-snapshots=missing --project=firefox  tests/smoke.spec.js
```

Then for the full regeneration:

```fish
npx playwright test --update-snapshots=missing
```

Once everything has a Linux baseline, switch to `changed` for day-to-day work — that way `--update-snapshots` only rewrites the snapshots you've actually broken with a code change, not the ones that still pass.

## What to do about line endings instead

Playwright doesn't normalize CRLF in text snapshots. Three real options, in order of robustness:

### Option 1 (recommended): `.gitattributes` at repo root

Create `.gitattributes` in the repo root with:

```
* text=auto eol=lf
*.png binary
*.jpg binary
*.mp3 binary
```

This tells Git to normalize all text files to LF on checkout (regardless of OS) and to PNG/audio as binary. New checkouts on Windows will also get LF, so cross-platform snapshot consistency is enforced. Existing checked-out files will normalize on the next `git add`.

After creating the file, normalize what's already on disk:

```fish
git add --renormalize .
git status   # see what changed
```

If existing `-win32.txt` snapshots get rewritten as LF, that's expected — they'll still match on Windows because Playwright's `innerText()` on Windows Chromium may return `\n` or `\r\n` depending on version, and your tests will tell you which. (Modern Chromium returns `\n` on `innerText()` regardless of OS — the original CRLF assumption may have been wrong from the start.)

### Option 2: One-shot sed on existing snapshots

If you just want to clean up the committed `.txt` snapshots without touching Git config:

```fish
sed -i 's/\r$//' tests/*-snapshots/*.txt
```

Then commit. Future snapshots written by Playwright on Linux will already be LF, so they'll match. Future Windows checkouts will get LF too (unless your Git config has `core.autocrlf=true` on Windows, which would re-introduce CRLF — `.gitattributes` is the better fix).

### Option 3: Normalize in test code

If you have specific tests that compare strings across platforms, wrap them inline:

```js
const text = (await page.locator("#main-textarea").inputValue()).replace(/\r\n/g, '\n');

```

More invasive, less reliable — only do this if options 1+2 don't catch everything.

## Most likely culprit: the `expect` block we added

The `TypeError` pattern (`'regex'` and `'raw'`) is happening inside Playwright's aria-snapshot code path. The `expect` configuration block we added might be triggering it if it's in the wrong place or has an unexpected interaction. Let me see what you actually have — please share:

The `expect` block must sit at the **top level** of `defineConfig`, not inside `use`. Correct shape:

```js
export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  // ...
  expect: {                              // ← top level, sibling of `use`
    toHaveScreenshot: {
      maxDiffPixelRatio: 0.01,
      animations: 'disabled',
    },
  },
  use: {
    baseURL: 'http://localhost:3004',
    trace: 'on-first-retry',
  },
  // ...
});
```

If `expect` ended up inside `use` by accident, Playwright silently ignores the schema mismatch in some versions and tries to apply it as a per-test option, which can manifest as these internal TypeErrors.

## About the `merge-line-mismatch` failure

This one is a separate, real issue and won't be fixed by any of the above:

```
Locator:  getByText('⚠ Line count mismatch (4 vs 5)')

```

Test presses `Control+6` to trigger a merge with mismatched line counts and expects a warning toast. The toast never appears. Most likely cause: **KDE is intercepting `Control+6`** before Chromium sees it. Plasma's "Switch to Desktop N" shortcuts bind to `Control+number` by default on multi-desktop setups.

Quick check:



If the warning appears in a real browser when you press `Control+6` manually but not under Playwright, it's a keyboard event interception issue at the OS or compositor level.

Don't investigate this until the TypeError is resolved — it's currently masking whether the rest of the test would pass.

**Found it.** The TypeError is caused by parentheses in unquoted aria snapshot text. Look at your `hide-secondary-1.aria.yml`:

```yaml
- text: ( ) ⚠ Line count mismatch (5 vs 0)
- textbox "Secondary 1 lyrics": (Ojalá pudiera identificar ese olor) (Ese olor) ...
```

Both lines have unquoted text starting with `(`. Compare to your working `landing.yml`:

```yaml
- link "Issues (Ctrl+[)":     # parens inside quotes — fine
    - /url: https://...
- text: Now playing            # plain text, no leading paren — fine
```

Playwright's aria snapshot parser tokenizes values that start with `/` as regex literals. When a value starts with `(`, the tokenizer appears to misinterpret it as the start of a regex group, then crashes when it tries to access `.raw` on the regex object it expected to construct. Quoted strings (like `"Issues (Ctrl+[)"`) bypass this code path, but unquoted text values starting with `(` hit it.

This is a Playwright bug. Parens in translation text are intrinsic to your app — you can't avoid them.

## Fix strategy: replace `toMatchAriaSnapshot()` in affected tests

The aria snapshots that contain unquoted leading-paren text will always crash Playwright. Three options:

### Option 1: Replace aria snapshot calls with explicit assertions (recommended)

For each test that crashes, replace `toMatchAriaSnapshot()` with explicit locator checks. Example for `hide-secondary`:

```js
// Before
expect(page.locator("#editor-area")).toMatchAriaSnapshot();

// After — assert what you actually care about
await expect(page.getByText("Secondary 1")).toBeVisible();
await expect(page.getByText(/Line count mismatch/)).toBeVisible();
await expect(page.getByRole("button", { name: "Import secondary lyrics file" })).toBeVisible();
await expect(page.getByRole("textbox", { name: "Secondary 1 lyrics" })).toBeVisible();
```

More verbose, but more reliable, more readable, and doesn't depend on Playwright's fragile aria serializer.

### Option 2: Quote the offending aria snapshot lines manually

Edit each `.aria.yml` file to wrap the parenthesized text in quotes:

```yaml
# Before
- text: ( ) ⚠ Line count mismatch (5 vs 0)

# After
- text: "( ) ⚠ Line count mismatch (5 vs 0)"
```

This works for comparison but **Playwright will overwrite your edits** the next time someone runs `--update-snapshots`. Not a durable fix.

### Option 3: File a Playwright bug and wait

This is genuinely a Playwright parser bug. Report at https://github.com/microsoft/playwright/issues with your `hide-secondary-1.aria.yml` as a reproduction case. Won't help you today.
