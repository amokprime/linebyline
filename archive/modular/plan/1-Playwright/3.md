```fish
function tst
  if not test -f playwright.config.js
    echo "tst: not in a Playwright repo (no playwright.config.js in $PWD)"

    --exclude=.git --exclude=node_modules \
    --exclude=playwright-report --exclude=test-results \
    --exclude=.cache --exclude=.next --exclude=dist \
    ./ $remote:$remote_root/

  # Same one-shot invocation, just executed on the remote
  ssh -t $remote "
    podman pull -q $image >/dev/null 2>&1;

      -v $remote_root:/workspace -w /workspace \
      -v ~/.local/share/podman-npm-cache:/tmp/.npm \
      -e HOME=/tmp -e NPM_CONFIG_CACHE=/tmp/.npm \
      -e NPM_CONFIG_UPDATE_NOTIFIER=false -e PW_CONTAINER=1 \
      $image npx playwright test \$argv
  "

  # Pull HTML report / traces back so you can `npx playwright show-report` locally
  rsync -az --delete $remote:$remote_root/playwright-report/ ./playwright-report/ 2>/dev/null
  rsync -az --delete $remote:$remote_root/test-results/    ./test-results/    2>/dev/null

```

- `rsync --delete` over LAN is sub-second for a docs-sized tree, captures uncommitted edits (git can't, since you pre-commit), and excludes the heavy dirs so `node_modules` lives only inside the container on the remote.
- `ssh -t` allocates the TTY so Playwright's progress output looks identical to local. Podman still does the one-shot `--rm` lifecycle — no Compose stack, no idle memory on the Docker host.
- `podman pull -q` is a no-op when the image is cached, so the first run pays the ~1 GB pull once and subsequent runs start instantly.
- The `set -l remote playbox` is the only line you change between machines. Define it in `~/.ssh/config`:
  ```
  Host playbox
      HostName 192.168.x.x
      User you
      IdentityFile ~/.ssh/id_ed25519
  ```
- Results sync is best-effort (`2>/dev/null`) so the function's exit code is the test's exit code, which is what the pre-commit hook actually gates on.

To keep Fish/Bash from drifting, generate a `tst.sh` from the Fish function at function-load time so OMP's Bash agent and your interactive shell share one source of truth:

```fish
# Add to the end of tst.fish
function _tst_emit_bash
  set -l out ~/.local/share/tst.sh
  echo "# generated from tst.fish on "(date -Iseconds)" — do not edit" > $out
  # Dump the body of this function as text
  functions tst | tail -n +2 >> $out      # drop the `function tst` header
  # The trailing "end" is unwanted in Bash; replace the Fish-only constructs
  sed -i -e 's/^end$//' -e 's/^function /tst() {/' $out
  chmod +x $out
end
_tst_emit_bash
funcsave tst
```

**`rsync` from `.gitignore`** — yes, and the snippet above does it. The gotcha: `rsync` filter rules differ from git's in two ways, both handled:

1. Git `!pattern` re-include rules → flip to `rsync`'s `--include=pattern` (which must appear *before* the earlier `--exclude` that matched the parent dir). The loop builds them in order so the re-include lands at the right priority.
2. Git's anchored-vs-unanchored semantics: a leading `/` means "repo root" in both, but `rsync` source patterns are always relative to the transfer root, so plain `dist/` works the same in both. The one case to watch is anchored globs like `/build` — those need to be rewritten to `build` when the transfer root is `./`. Quick patch if you hit a false exclude:

```fish
# inside the read loop, after the trim:
if string match -q -- '/*' $line
  set line (string sub -s 2 -- $line)   # drop the leading /
end
```

If the gitignore gets gnarly (negations, deep re-includes), skip parsing it and use `git ls-files` instead — that is the authoritative file list:

```sh
git ls-files -zco --exclude-standard \
  | rsync -az --delete --exclude-from=- --exclude=.git \
        ./ $remote:$remote_root/
```

This is slower for huge repos but always correct because git resolves negation and directory rules for you.

**"Does the `rsync` setup force the remote to mirror the local state?"** — yes, the `-a --delete` combination does exactly that: every byte is overwritten, and any file present on the remote but absent locally is removed. So if you edit a file on the remote manually (e.g. inside a container that wrote a test artifact), it gets wiped on the next `tst` run. That's fine for the working tree but means the remote `~/playwright-runs/$project` must never hold anything you want to keep — which is why the snippet also excludes `playwright-report/` and `test-results/` (no point re-syncing things Playwright will overwrite in five seconds). If you ever do want to keep a remote-side scratch file, drop the `--delete` and accept the drift, or use a dedicated scratch path outside `remote_root`.

One subtlety to be aware of: `--delete` deletes *excluded* files too. So if you had a one-off `notes.md` in the remote tree that wasn't in your local tree, `-a --delete --exclude=notes.md` would still delete it (exclude means "don't send", not "don't remove"). To preserve remote-only files, use `--delete-excluded` (default) vs. `--delete-after` plus a `--max-delete` guard if you're nervous:

```sh
rsync -az --delete --max-delete=50 ./ $remote:$remote_root/
```

For pre-commit usage the plain `--delete` is what you want — the remote should always look like your local repo, full stop.

## "Stay logged in between tests" — three real options

**Option A: ControlMaster (recommended, zero setup on the server)**

Add one line to the `Host playbox` block in `~/.ssh/config`:

```
    ControlMaster auto
    ControlPath ~/.ssh/sockets/%r@%h:%p
    ControlPersist 10h
```

```sh
mkdir -p ~/.ssh/sockets && chmod 700 ~/.ssh/sockets
```

Now the first `ssh playbox` (or the first `rsync`/`git` to it) opens one TCP connection and authenticates once. Every subsequent command — OMP's `tst.sh`, your interactive `ssh playbox`, the post-run `rsync` pulling `playwright-report/` back — multiplexes over that same socket without re-authenticating. It feels like being logged in because the prompt returns instantly. `ControlPersist 10h` keeps the master alive for 10 hours after the last use, so a coffee break doesn't break it. Drop to `0` to close it as soon as the last session exits.

This is the only one that requires nothing on the server.

**Option B: systemd user service that holds an autossh tunnel**

Heavier, but useful if OMP also needs to reach other services on the playbox (e.g. a long-lived dev server). Not needed for your `tst` flow.

**Option C: Long-lived interactive SSH session inside a `hub start` process**

The OMP `hub` tool already exists for this. Define a named process:

```sh
hub start --name playbox-ssh ssh -N playbox    # -N = no command, no TTY
```

Then in `tst.fish` replace `ssh -t $remote "…"` with `hub send --name playbox-ssh --text "…"` (or just call `ssh` over the ControlMaster socket — option A and `hub` are not mutually exclusive; `hub` is for cases where you want OMP to be able to inspect the process). For your use case Option A is enough and one less moving part.

## What each field actually means

```
Host Fedora-Server
    HostName fedora
    User user
    IdentityFile ~/.ssh/id_ed25519
    AddKeysToAgent yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

- **`Host Fedora-Server`** — a pattern that matches whatever you type on the command line. It's an arbitrary label, scoped to this file. `ssh Fedora-Server`, `scp Fedora-Server:foo ./`, `rsync ./ Fedora-Server:~/` all match. You can have many `Host` blocks and they cascade: the first match wins, then any following `Host *` block applies as a default. Rename it to `deskbox`, `playbox`, `fez` — it doesn't matter; only you ever see it.
- **`HostName fedora`** — what the *system* actually tries to connect to. `fedora` will only resolve if Avahi/mDNS is running (it is by default on Fedora) and broadcasts `fedora.local`. The usual reliable form is `fedora.local` or the static IP `192.168.x.x`. The static IP is what you want for pre-commit, so a router hiccup or DHCP lease change doesn't break the run.
- **`User user`** — the login name on the *server*. There is no requirement that client and server usernames match; if your main box is `me@main` and the playbox is `me@deskbox`, leave `User` unset and `ssh me@deskbox` or just `ssh deskbox` (which uses your local username by default). Setting `User` to your desktop username is only useful when the two accounts differ.
- **`IdentityFile ~/.ssh/id_ed25519`** — which private key on *this* (client) machine to offer. The server doesn't see this path; it sees a public-key signature attempt and decides accept/reject based on `~/.ssh/authorized_keys` over there.
- **`AddKeysToAgent yes`** — the comment in my prior message was confusing; the "alias" being "dropped" is just *not* setting `Host` / `Host` aliases for the key. `AddKeysToAgent yes` means: when SSH uses this key for the first time in a session, automatically hand it to the running `ssh-agent` (which is wired to KWallet on Fedora). You don't need a separate `ssh-add` step afterwards, but running it once after `ssh-keygen` is harmless and makes the key available immediately. Once in the agent, all other SSH connections from any process on your desktop session reuse it without re-prompting.
- **`ServerAliveInterval 30`** — every 30 seconds of *inactivity* the client sends a tiny keepalive packet. Counterintuitively, this is to detect a dead network so the master socket (Option A from the previous message) tears down cleanly. It is **not** an auto-logout; the server has its own `ClientAliveInterval` for that, and the default is 0 (no timeout). With `ClientAliveInterval` unset on the server, your session lives forever. With `KeepAlive yes` (the Fedora default), it lives until either side's TCP stack decides the connection is dead.
- **`ServerAliveCountMax 3`** — three missed keepalives in a row = 90 seconds of silence = the client gives up and closes the master socket. So "after 30 days" is wrong; the relevant number is the *idle* gap, not calendar time. It does not affect an actively running test; only the dormant master.

```sh
# on the playbox, in ~/.config/syncthing/config.xml under <device id=...> or <folder ...>:
<folder id="linebyline" path="/home/user/GitHub/linebyline" ...>
    <fsWatcherEnabled>true</fsWatcherEnabled>
    <fsWatcherDelayS>1</fsWatcherDelayS>
    ...
</folder>
```

`fsWatcherEnabled` uses `inotify` under the hood, so changes are picked up in milliseconds, not seconds, with no polling cost. Then the OMP loop is:

1. OMP runs `~/.local/share/tst.sh` (Bash version, generated from Fish).
2. Test fails. OMP reads the failure from the captured output.
3. OMP edits the file in the local tree.
4. Syncthing `inotify` sees the change, pushes to playbox within ~100 ms.
5. OMP reruns `tst.sh`. The playbox already has the fix.

That latency is shorter than the `rsync` cold-start and the loop is more robust because the working tree on the playbox is always current — no `--delete` race, no "I edited on the playbox, the next rsync wiped it" hazard.

**Generate the Bash version** still applies (your original concern about Fish/Bash drift); same `_tst_emit_bash` helper from earlier. With Syncthing the function is so short that the generated `tst.sh` is essentially the same script with `function tst/end` replaced by `tst() { }`.

- You're not already running Syncthing and don't want a permanent daemon.
- The folder is large enough that real-time mirroring costs meaningful I/O.
- You want the deletion guarantee (Syncthing doesn't delete files; it only mirrors adds/updates).

For a docs site with sub-second commits, none of those apply. Syncthing is the right call.

Two storage drivers are at play, and Fedora's default has been a moving target:

**On the playbox (2.47 GB):** almost certainly the **`overlay`** driver. Podman uses a separate upperdir for each container; the image's lower layers are stored as plain tarballs on disk and only assembled into a unified view at container start. `podman images` reports the lower-layer *unpacked* size, but `overlay` deduplicates files that are byte-identical between layers (e.g. apt package indexes, locale data) using *inode-level* sharing, so the on-disk footprint is closer to the *unique* bytes per layer rather than the sum.

**On the main box (4.51 GB):** likely the **`vfs`** driver, or an older overlay setup without the same dedup. VFS is the "extract every layer to its own directory tree, no sharing" fallback that Podman falls back to when the kernel doesn't support overlayfs (e.g. running inside a container, a non-standard rootfs, or `storage.conf` forcing it). VFS is what gives you the full 4.51 GB because every layer is materialized independently.

## How SSH handles multiple keys

The model is: **the agent holds an unordered set of unlocked private keys**; the SSH client offers them in order to whatever server is being authenticated against, and the server picks the first one that matches a line in its `authorized_keys`.

- `ssh-add -l` lists everything currently in the agent. You'll see one entry now (the GitHub key).
- `ssh-add ~/.ssh/id_ed25519_playbox` adds a second one. From that point, `ssh-add -l` shows two.
- `ssh github.com` and `ssh playbox` both try *all* loaded keys. GitHub rejects the playbox key (it's not in their `authorized_keys`), the playbox rejects the GitHub key (same reason), each server accepts the right one on the second try. This is invisible to you because OpenSSH suppresses the failed offers unless you pass `-v`.
- The client doesn't know which key belongs to which server. The `~/.ssh/config` `IdentityFile` line tells it which key(s) to *offer*; the agent's contents determine what's *available*. With `AddKeysToAgent yes` and `IdentitiesOnly` not set, SSH will offer both, and the right one wins per-server.

## The right move here

Generate a *separate* keypair for the playbox, push the public half to the playbox, and let the agent hold both:

```sh
ssh-keygen -t ed25519 -C "PC→playbox" -f ~/.ssh/id_ed25519_playbox
# passphrase: yes, same one as the GitHub key is fine — KWallet stores it by key path
```

- The *file* is the second private key, alongside the existing `id_ed25519` (which still auths to GitHub).
- The *passphrase* can be the same or different; KWallet stores an entry per key path, so two keys with the same passphrase still get two separate `ksshaskpass` prompts the first time, but after you check "Remember password" for each, both are silently unlocked on subsequent boots.
- The playbox gets the public half: `ssh-copy-id -i ~/.ssh/id_ed25519_playbox.pub user@<playbox>`.
- Update `~/.ssh/config` so the playbox *only* offers the playbox key — this is the cleanest pattern, avoids GitHub ever seeing the new key, and means you can revoke one without touching the other:

```
Host playbox
    HostName <playbox-static-ip-or-.local>
    User user
    IdentityFile ~/.ssh/id_ed25519_playbox
    IdentitiesOnly yes            # ← critical: only offer the playbox key to playbox
    AddKeysToAgent yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
    ControlMaster auto
    ControlPath ~/.ssh/sockets/%r@%h:%p
    ControlPersist 10h

Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
```

`IdentitiesOnly yes` is the bit that prevents the "agent offers everything" behavior for a specific host. Without it, even though `IdentityFile` is set, the agent still tries every loaded key after the explicit one fails. With it, only the named key is offered. For your GitHub key you almost certainly want this too — it stops the playbox key from ever being sent to github.com (a small privacy thing: GitHub would see you tried to authenticate with a key they don't have).

ASSISTANT: **Found it.** The socket exists, but the master process behind it has been dead for ~32 minutes (socket `srw------- 1 user user 0 Aug 14 19:46`, current time is 20:20). The "ControlSocket ... already exists, disabling multiplexing" line in your `ssh -fN` output is the smoking gun: OpenSSH found the *socket file* (which survived because nothing cleaned it up) but couldn't connect to the *master process* behind it (which exited), so it printed that warning and ran the connection as a fresh, non-multiplexed SSH. That's why subsequent `time ssh Server 'true'` calls were still 175–180ms.

Three things are happening:

1. **`-fN` (fork, no command) exits as soon as it logs in.** I told you `-fN` would hold the master, but on Fedora 44 / OpenSSH 10.2 the behavior is: the master is held only while the foreground command runs, and `-N` means "no command" — which means "exit immediately after auth." The master process forks off briefly to set up the socket, then exits. The socket file stays behind as a stale marker, and every future SSH call hits the "already exists, disabling multiplexing" path.

2. **The autostart at 13:25 created a master that lived only as long as the autostart's `ssh-add` runs.** When `ssh-add` finishes (which is microseconds after the keys are loaded), the SSH subprocesses spawned by it exit, taking the master with them. `ControlPersist 10h` doesn't help here because the master *was never kept alive* — it was a transient helper, not a persistent connection.

3. **The proper invocation is `ssh -M -N -f Server`** — the `-M` flag explicitly tells OpenSSH to put the connection into "master mode" and stay in the foreground (or background, with `-f`). Without `-M`, OpenSSH only enters master mode when it can promote an existing connection, which never happens for `-N`-style invocations.

The recipe that actually works:

```sh
ssh -M -N -f -o ControlPath=~/.ssh/sockets/%r@%h:%p Server
# -M: master mode (this connection IS the master)
# -N: no remote command
# -f: fork to background after auth
# -o ControlPath: same path your config uses (or just rely on ~/.ssh/config)
```
