## Side question: are `my-systemdcoredum.te` / `.pp` related to the Webkit crashes?

**Yes, indirectly — but they are NOT Ubuntu core dumps, and adding them to `.gitignore` was the right call.**

From the earlier chat log in `1_Playwright-2.md` (around the SELinux AVC discussion), here's the chain:

1. WebKit's `WPEWebProcess` crashes during teardown after every webkit test run (inside the Podman Ubuntu container).
2. `systemd-coredump` on your **Fedora host** (not the container) wakes up to capture the crash.
3. `systemd-coredump` sends `signull` to the crashed process to check if it's still alive.
4. SELinux on Fedora blocks that signal because the target is `spc_t` (Podman's super-privileged container context), source is `systemd_coredump_t`.
5. You ran `sudo ausearch -c 'systemd-coredum' --raw | audit2allow -M my-systemdcoredum` then `sudo semodule -X 300 -i my-systemdcoredum.pp`. The output of that `audit2allow` step is the `.te` (Type Enforcement source) and `.pp` (compiled policy module).

So:

- **`.te` / `.pp` are SELinux policy files, not core dumps.** Ubuntu core dumps would live in `/var/lib/systemd/coredump/` and have names like `core.WPEWebProcess.*.zst`. Your files are Fedora host artifacts.
- **They're benign.** The earlier chat already established the AVC is harmless — the WPEWebProcess teardown crash doesn't affect any test results (tests have already finished by then), and you don't need the core dump.
- **The "coredum" spelling (missing final `p`) is just `audit2allow` truncating the `comm=` field to 15 chars.** `systemd-coredum` is the truncated process name; `my-systemdcoredum` is what `audit2allow -M` named the module based on that.
- **`.gitignore` entry is correct.** These are host-specific SELinux policy modules. They shouldn't be committed; they only matter on your Fedora host with SELinux enforcing + Podman + systemd-coredump. Other contributors (or CI, which is Ubuntu in GitHub Actions) don't need them.
- **One caveat:** if you ever nuke this machine or `semodule --remove`, you'll lose the policy and the AVCs come back. Since they're benign, that's fine — but if you want a record of "I did this once," drop a one-liner in `archive/modular/plan/` (e.g. `selinux-systemdcoredump.md`) noting the `audit2allow` command, so future-you can recreate it.

The Webkit crashes themselves don't appear in `tst.log` because Playwright treats them as post-test teardown noise — the test result is already recorded before the crash happens. The 36 failures in your log are all assertion failures, not crashes.

## The serious one: WebKit dark-mode dropdown bug

I cropped the divergent region (columns ~240–285, the font-family `<select>`) and ran a side-by-side VLM comparison. Verdict:

- **chromium-linux & firefox-linux**: dropdown renders dark, white chevron arrow, "Serif" text in light color — correct.
- **firefox-win32**: same as firefox-linux — correct.
- **webkit-linux**: dropdown renders with a **white background**, dark arrow, light text on white — broken dark theme.

This is the source of the ~21% pixel diff between webkit and the other two. It's not a rendering quirk; it's a real CSS bug in the app, not in the test.

**Likely cause** (without seeing `docs/index.html`): one of

1. Missing `<meta name="color-scheme" content="dark">` in the document head — without this hint, WebKit refuses to dark-theme native form controls even when the rest of the page is dark.
2. Missing `-webkit-appearance: none` (or the modern `appearance: none`) on `<select>` elements, so WebKit falls back to the OS-default light rendering.
3. CSS that sets `background-color` on the `<select>` but not on the `<option>` children, which on WebKit renders the closed-select background using the OS theme.

Chromium and Firefox both auto-dark-theme form controls when the page has dark backgrounds; WebKit does not, so the bug only shows up there.

**Real-world impact**: this is a user-visible bug for Safari users on macOS/iOS. Worth fixing for its own sake, not just for the test.

**Fix shape** (cheap to try, in order):

```html
<!-- docs/index.html head -->
<meta name="color-scheme" content="dark light">
```

If that alone doesn't fix the webkit screenshot, add to your CSS:

```css
select {
  appearance: none;
  -webkit-appearance: none;
  background-color: var(--your-dark-bg); /* explicit */
  color: var(--your-dark-fg);
}
```

Then regenerate `titlebar-dark-webkit-linux.png` (only that file — `tst --project=webkit -g "titlebar-dark" --update-snapshots`) and verify the dropdown now renders dark.
