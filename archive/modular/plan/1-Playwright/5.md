## Root cause: `playingLine` lags behind `audio.currentTime`

The "blue highlighter" / "bold text" / "blue timestamp color" you're seeing are all the **`.active` class** applied to the "playing line" (`docs/index.html:990`):

```js

if(i===activeLine)div.classList.add('cursor');
```

The `playingLine` variable is **only** updated by `onTimeUpdate()` → `updateActiveLineFromTime()` (`docs/index.html:1107-1126`), which fires on HTML5 `timeupdate` events (~250 ms intervals, browser-paced).

Now look at `replayActiveLine()` (`docs/index.html:1188-1199`):

```js
function replayActiveLine(seekEnd){
  if(activeLine<0||!audioEl)return;
  const lines=getTA().split('\n');

  if(ms!==null){

```

Notice what it does **not** do:
- Does not set `playingLine`
- Does not call `renderMainLines()`
- Does not wait for the seek to settle

## The v4 fix: synthetic `timeupdate` event

Instead of **waiting** for `timeupdate` to fire naturally, **dispatch it synchronously** via `page.evaluate()`:

```js
async function triggerTimeUpdate(page) {
  await page.evaluate(() => {
    const audio = document.querySelector("audio");
    if (audio) audio.dispatchEvent(new Event("timeupdate"));
  });
}
```

This calls `onTimeUpdate()` (registered at `docs/index.html:1088`), which:
1. Reads `audioEl.currentTime`
2. Sets `#time-pos` text
3. Calls `updateActiveLineFromTime(pos * 1000)` → sets `playingLine` → calls `renderMainLines()` → adds `.active` class

All synchronous, no waiting for browser-paced events.

### Why the result is deterministic

`onTimeUpdate` reads `audioEl.currentTime`. After `seekNextLine()` sets `audioEl.currentTime = 2.46`, the value might be:
- **0** (seek hasn't completed yet — WebKit sometimes returns old value)
- **2.46** (seek completed — Chromium/Firefox return new value immediately)

But `updateActiveLineFromTime` picks the last line whose timestamp ≤ `currentTime`:

| Test | Seek target | `currentTime=0` → `best` | `currentTime=target` → `best` | Same? |
|---|---|---|---|---|
| `replay-r` | 2.46s | line 0 (ts=0 ≤ 0) | line 0 (ts=0 ≤ 2460, ts=3060 > 2460) | ✅ |
| `replay-moving-next` | 2.46s | line 0 | line 0 | ✅ |
| `replay-sync-time` | 3.46s | line 0 | line 0 (ts=0 ≤ 3460, ts=4060 > 3460) | ✅ |
| `replay-shift+r` | 9.91s | line 0 | line 9 or 10 (boundary) | ❌ (but each browser has own baseline + `maxDiffPixelRatio:0.1`) |

For the three previously-flaky tests, `.active` lands on **line 0** regardless of whether the seek has completed. The screenshot is deterministic.

For `replay-shift+r`, the boundary case (9.91s = line 10's timestamp) means `.active` could be on line 0 (if seek hasn't completed) or line 9/10 (if it has). But each browser has its own baseline from the regen, and `maxDiffPixelRatio: 0.1` covers run-to-run variation on the same browser.
