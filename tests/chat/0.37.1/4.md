## Diagnosis: why webkit still times out

The `replay-sync-time` locator is `getByText("[00:00.00] I wish I could identify that smell[00:04.06] That smell [00:06.35]")`. This is smushed across **two layers** of element boundaries:

1. **Within a line**: `<span class="ts">[00:00.00]</span><span> I wish…</span>` — the timestamp and lyric are in separate siblings.
2. **Across lines**: the `ul#main-lines` parent's `textContent` is the concatenation of all `.lrc-line` divs with no separator, because the JS uses `appendChild` (no source whitespace).

Chromium and Firefox's text matchers happily return `ul#main-lines` for the smushed substring. WebKit's matcher treats the span/div boundaries differently and the substring never resolves within the 5s `toHaveScreenshot` timeout — so the test fails before any screenshot is even compared.

The same root cause is in `sync-start-end` (`getByText("0:020:13")` for smushed `#time-pos`+`#time-dur`) and `adjust-time` (`getByText("[00:00.10] I wish I could")` for the timestamp+lyric substring).

`replay-sync-time` has a **second** problem on top: the `[00:04.06]` is the *adjusted* timestamp computed from `audio.currentTime` when "c" is pressed. Linux audio decoding drift means webkit lands at a slightly different position than chromium, so even if the locator resolves the rendered digits differ and the screenshot won't match. That's why I added `maxDiffPixelRatio: 0.10` to that one test only.

## Cluster 1 migration — commentary

### The three brittle patterns

Three patterns in the original `sync-adjust.spec.js` were failing on webkit (and one of them on all 3 browsers). All three are `getByText(...)` calls that rely on text being joinable across element boundaries — which WebKit's text matcher doesn't do the same way as Chromium/Firefox.

#### 1. `getByText("[00:00.00] I wish I could")` — timestamp + lyric substring

The DOM built by `docs/index.html` for each lyric line is:

```html
<div class="lrc-line" role="listitem">
  <span class="ts">[00:00.00]</span>
  <span> I wish I could identify that smell</span>
</div>
```

Chromium and Firefox's text matcher happily returns the parent `.lrc-line` for the substring `[00:00.00] I wish I could`. WebKit's matcher treats the two `<span>` siblings as separate text nodes and the substring never resolves within the 5s `toBeVisible` timeout.

Affected tests: `sync-start-end`, `adjust-time`, `adjust-seek`.

#### 2. `getByText("0:020:13")` — smushed `#time-row` spans

`#time-row` in `docs/index.html` looks like this:

```html
<div id="time-row">
  <span id="time-pos" aria-label="Current position">0:00</span>
  <span id="time-dur" aria-label="Duration">0:00</span>
</div>
```

No whitespace between the two `<span>` tags in the source, so the parent `#time-row` has `textContent === "0:000:00"`. The original test asserts `getByText("0:020:13")`, which depends on:

- the audio file being **exactly** 13 seconds long (so `#time-dur` is `0:13`)
- the audio having played to **exactly** 0:02 at assertion time (so `#time-pos` is `0:02`)

Linux audio decoding is non-deterministic enough in the Ubuntu container that this fails intermittently on all 3 browsers, and consistently on webkit.

Affected test: `sync-start-end`.

#### 3. `getByText("[00:00.00] ...smell[00:04.06] That smell [00:06.35]")` — multi-line smushed locator

This targets `ul#main-lines` via `textContent` concatenated across sibling `.lrc-line` divs (which the JS builds with `appendChild`, so there's no source whitespace between them either). The smushed substring `[00:00.00] ...smell[00:04.06] That smell [00:06.35]` resolves on chromium/firefox but never on webkit, so the `toHaveScreenshot()` assertion times out before any screenshot is even compared — that's why `replay-sync-time` had no webkit baseline before your `--update-snapshots` run.

The `[00:04.06]` value is also audio-position-dependent: it's the adjusted timestamp computed from `audio.currentTime` when "c" is pressed. Linux audio decoding drift means webkit lands at a slightly different playback position than chromium, so even when the locator resolves the rendered digits differ and the screenshot won't match.

Affected tests: `replay-r`, `replay-shift+r`, `replay-moving-next`, `replay-sync-time`.

### Fix strategy

Mirrors `fields-merge.spec.js`. Three patterns:

| Assertion type | Old approach | New approach |
|---|---|---|
| Text content (timestamp + lyric) | `getByText("[00:00.00] I wish I could")` | `lyricLinesText(page)` then `expect(lines).toContain("[00:00.00] I wish I could")` |
| Time-row span text | `getByText("0:020:13")` | `expect(page.locator("#time-pos")).toHaveText(/^0:0[1-3]$/)` and `expect(page.locator("#time-dur")).toHaveText(/^0:1[2-4]$/)` — regex tolerates ±1s of audio drift |
| Screenshot of lyric list | `getByText("...smushed...").toHaveScreenshot()` | `page.getByLabel("Lyric lines").toHaveScreenshot()` — same `ul#main-lines` element, existing baselines remain valid |

The `lyricLinesText(page)` helper is the same one `fields-merge.spec.js` uses — `innerText()` preserves visual line breaks between listitems and gives a stable cross-browser string.

For `replay-sync-time` only, I added `maxDiffPixelRatio: 0.10` to the `toHaveScreenshot` call. This tolerates the adjusted `[00:04.XX]` digit differences between browsers when audio drift lands webkit on a slightly different playback position. 10% pixel ratio is generous — a few characters of timestamp text is well under that.

### Why existing baselines should still match

For the four `replay-*` tests, `getByText("...smushed...")` was already resolving to `ul#main-lines` (the smallest element whose `textContent` contained the full smushed string). `getByLabel("Lyric lines")` resolves to the same `ul#main-lines` (which has `aria-label="Lyric lines"` per `docs/index.html`). Same element, same bounding box, same screenshot. Chromium and Firefox baselines should match without regeneration.

### Tests left unchanged

Three tests in the file were already passing on all 3 browsers and didn't use the brittle patterns, so I left them alone:

- **`replay-resume`** — uses `page.locator("#audio-box").toContainText("0:01")`, which is already robust against the smushed-span problem (Playwright's `toContainText` walks all descendant text nodes and concatenates them with whitespace normalization).
- **`replay-another-line`** — uses `getByText("[00:03.06] That smell").click()`. Single-line locator, so Playwright's deepest-match returns the `.lrc-line` div reliably on all browsers. Click semantics work where substring visibility doesn't. No change needed.
- **`sync-empty`** — uses `toMatchAriaSnapshot()`. Out of scope for Cluster 1 (that's the same family of crashes as Cluster 3 in the original triage — `import-paste.spec.js` aria bugs). If you want it migrated too, that's a separate conversation.
